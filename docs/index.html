01 / Architecture

The current cognitive stack

The architecture separates general model capability from runtime cognition. The model provides learned behavior; the runtime supplies explicit state, tools, verification, memory access, and feedback.

  • Foundation model for language, abstraction, coding, and general reasoning.
  • Thinking controller for difficulty, uncertainty, compute, branching, verification, and stopping.
  • Agent loop for tool execution, observation handling, recovery, and task completion.
  • External memory for durable experience without requiring every episode to become a weight update.
  • Persistent interaction traces as raw material for later continual-learning passes.

Execution flow

Reasoning becomes a closed loop

01 / TASK

Parse the objective, constraints, desired output, dependencies, risk, and success criterion.

02 / STATE

Maintain goal, known facts, unknowns, evidence, and task/plan state rather than relying on raw transcript alone.

03 / STRATEGY

Choose the smallest sufficient reasoning, retrieval, tool, or verification strategy.

04 / ACTION

Execute one useful step, then treat its output as an observation that can change the plan.

05 / VERIFY

Check the result against the actual success criterion before claiming completion.

06 / LEARN

Persist only durable experience with scope, evidence, applicability, and exclusions.

02 / Reasoning

Use compute when it buys information

Adaptive compute

Do not overthink the easy cases

Trivial deterministic questions can be answered directly. Harder tasks can escalate compute, branching, and verification when uncertainty or consequence warrants it.

Hypotheses

Keep alternatives alive when needed

Multiple plausible causes should remain explicit until discriminating evidence supports a commitment.

Verification

Prefer hard evidence

Tests, compilers, exact checks, schemas, environment state, and source evidence can verify claims more strongly than model confidence alone.

03 / Agentic execution

Reason. Act. Observe. Re-plan.

Failure is an observation, not a dead end

  • Inspect tool output instead of assuming a success status means useful data exists.
  • Change the strategy after repeated failure rather than blindly retrying.
  • Propagate new observations into dependent plan state.
  • Stop when the goal is satisfied or the evidence boundary has been reached.

04 / Memory

Memory is experience, not truth

EPISODIC

What happened

Interaction traces preserve concrete observations, failures, and outcomes without automatically converting every incident into a global rule.

PROCEDURAL

What tends to work

Repeated, verified episodes can become scoped procedures and lessons with conditions and exclusions.

FACT / HYPOTHESIS

What we currently believe

Facts and hypotheses remain distinct, with time and version context preserved so updates do not silently erase history.

Memory writes are gated because a powerful retrieval system can amplify a bad lesson just as easily as a good one.

  • Do not generalize a one-off incident without supporting evidence.
  • Preserve scope and applicability conditions.
  • Keep user preferences separate from global facts.
  • Use update or supersession when newer evidence changes the current state.

05 / Retrieval

Similarity starts retrieval; context decides reuse

A semantically close memory can still be wrong for the current version, environment, scope, or failure signature.

  • Re-rank by context, scope, recency, evidence quality, and environment match.
  • Demote superseded memories except when historical context matters.
  • Deduplicate repeated records and shared-source evidence chains.
  • Use memory as a hypothesis source, then verify against current evidence when volatility or risk is high.

06 / Continual learning

A staged path from conditioning to learned behavior

01 / SFT

Teach situation modeling, adaptive compute, verification, recovery, memory scope, and explicit runtime actions.

02 / REJECTION

Generate candidate trajectories and keep those that demonstrate useful strategy selection and verified outcomes.

03 / VERIFIER RL

Where objective checks exist, reward outcomes through tests, compilers, exact checks, schemas, or evidence consistency.

04 / MEMORY UTILITY

Train memory writes against delayed utility: write → future retrieval → future task outcome, including negative-transfer checks.

05 / AGENTIC RL

Train long-horizon trajectories for planning, action selection, observations, recovery, evidence quality, and completion.

08 / Research basis

Research behind the architecture

DeepSeek-R1

Verifier-driven reinforcement learning as evidence that useful reasoning behaviors can be shaped by checkable task outcomes.

 Search-R1

Search as part of the reasoning loop, supporting retrieval-aware control rather than lookup-only tooling.

 Deep Research Agents

Long-horizon research requires query strategy, evidence assembly, cross-validation, and stopping decisions.

 Verification

Explicit verification is a useful companion to generation in test-time reasoning systems.
Memory systems

The research synthesis also incorporates hierarchical retrieval, lightweight memory controllers, consolidation, and learned memory management from H-MEM, LightMem, AgeMem, and MemPO.

09 / Implementation

The runtime that exists today

01

Code execution

Python runs inside the workspace with a 30-second timeout and returns stdout, stderr, and exit status for inspection.

02

File state

Read/write operations are constrained to the workspace so external task state can be maintained safely.

03

Durable memory

Memory is stored as append-only JSONL records with type, scope, applicability, exclusions, evidence, and confidence.

10 / Boundaries

What the current evidence does not establish

NOT AGI

A working tool loop, external memory, and post-training are architectural components, not proof of general intelligence.

RETRIEVAL

The current runtime memory search is lightweight lexical scoring; contextual and hierarchical retrieval remain research work.

CONTINUAL LEARNING

Interaction traces are recorded as raw material. They are not automatically distilled back into model weights.

EVALUATION

The held-out set is designed to test architecture-level behaviors, but the repository does not currently publish a validated aggregate capability score for it.
